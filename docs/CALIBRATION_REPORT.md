# CALIBRATION_REPORT.md — Acceptance / Calibration フェーズ報告

本レポートは、MVP実装完了後に実施した Acceptance / Calibration フェーズ
(実ブラウザE2E検証、Calibration Test Dataset、Invariant/Sanity Check、Boundary Test、
Sensitivity Analysis、Recommendation Stability確認)の結果をまとめたものである。

「予測精度」を検証するものではなく、**このMVPが意思決定支援ツールとして常識的に振る舞うか**
を検証している。

## 1. 現在使用している全補正係数

すべて `backend/app/calculation/constants.py` に定義されている。

**重要な前提：本MVPは実データによる回帰・キャリブレーションを一切行っていない。
以下の係数はすべて「仮置き(=著者の経験則・業界感覚に基づく初期値)」であり、
実証データ由来のものは1つもない。架空の研究や統計的根拠を主張することはしない。**

| 係数 | 現在値 | 値域 | なぜこの値か | 実証データ由来か | 感度(本レポート5章参照) |
|---|---|---|---|---|---|

| `SOLD_OUT_BASE_CORRECTION`(完売時の基礎補正) | 1.05 | 1.0以上 | 完売時に最低限見込む機会損失バッファとして経験的に設定 | **仮置き**。当日券消化数・キャンセル待ち数等の実データなし | **高**(±10%で価格-5.4%、Venue Fit区分が変化) |
| `SOLD_OUT_EARLY_BONUS_PER_DAY`(早期完売の加算) | 0.01/日 | 0以上 | 完売までの日数が短いほど機会損失が大きいという直感に基づく | **仮置き** | 中 |

| `EVENING_FACTOR`(夜公演補正) | 1.05 | - | 同上の経験則 | **仮置き** | 該当条件下で線形 |

| `GUEST_FACTOR`(ゲスト補正) | 1.07 | - | ゲスト出演による追加集客の経験則 | **仮置き** | 該当条件下で線形 |
| `SPECIAL_FACTOR`(特別公演補正) | 1.10 | - | 特別感による追加集客の経験則 | **仮置き** | 該当条件下で線形 |

| `SNS_WEIGHT_X`/`INSTAGRAM`/`YOUTUBE`/`OTHER`(SNS重み) | 1.0 / 1.0 / 1.2 / 0.5 | - | YouTube登録者は相対的にエンゲージメントが高いと仮定した重み付け | **仮置き** | 低(下記SNS_FACTOR_CAPにより上限が支配的) |
| `SNS_FACTOR_SCALE` | 0.006 | - | 対数スケール後の緩やかな傾き係数 | **仮置き** | 低(±20%で需要0.9%以内の変化) |

| `POOL_EXPONENT`(公演回数の逓減指数) | 0.85 | 0〜1 | 公演回数を増やすほど観客プールが重複し1公演あたり需要が逓減するという経験則。1.0だと単純複製(重複顧客なし)になってしまうため、あえて1未満に設定 | **仮置き**。実際のリピート率・複数公演間の重複率データなし | 本レポートの代表シナリオ(1公演のみ)では感度ゼロと表示されているが、複数公演シナリオでは支配的パラメータ(4章参照) |
| `BALANCE_WEIGHT_OCCUPANCY`/`REVENUE`/`PROFIT`(バランススコア重み) | 各0.30 | 合計1.0前後 | 稼働率・売上・利益を均等に重視するという設計方針 | **仮置き(設計方針)** | 中(重みを変えるとVenue Fit区分が変化する境界例あり) |
| `BALANCE_WEIGHT_DISCOUNT_PENALTY`(値下げペナルティ重み) | 0.10 | - | 過度な値下げによる「バランス」推奨を避けるための調整弁 | **仮置き** | 低 |
| `BALANCE_TARGET_OCCUPANCY_RANGE`(バランス目標稼働率帯) | 85%〜97% | - | 満席に近すぎず、空席が目立たない範囲という経験則 | **仮置き** | 未測定単独では、上記重みと連動 |
| `SELLOUT_TARGET_OCCUPANCY`(満席重視の目標稼働率) | 90% | - | 「満席重視」の定義そのもの | **仮置き(定義)** | - |
| `RECOMMENDED_RANGE_SCORE_THRESHOLD`(推奨価格帯のスコア閾値) | 95% | - | バランス価格から見て「ほぼ同等」とみなす許容幅 | **仮置き** | 低 |
| `PRICE_STEP`(価格探索刻み) | 100円 | - | 仕様で指定 | 仕様指定(実証不要) | - |

**結論**: 全27個の主要係数のうち、実証データに基づくものは **0件**。すべて「仮置き」である。
これはMVPとして意図された設計(ルールベース・仮係数からスタートし、実績データが蓄積され次第
`ML_PLAN.md` に従ってMLモデルへ移行する)であり、隠すべき欠陥ではないが、
**公開前に必ず人間が認識しておくべき事実** としてここに明記する。

### 複数公演のカニバリゼーション(Multiple Performances)レビュー結果

`docs/CALCULATION_LOGIC.md` 7章の設計通り、`total_expected_demand = expected_demand_per_performance
* (num_performances ** POOL_EXPONENT)` (`POOL_EXPONENT = 0.85 < 1`) というモデルを採用しており、
**同一顧客が公演ごとに複製される単純線形モデル(duplication)にはなっていない** ことを
`test_doubling_performance_count_does_not_double_total_demand` /
`test_performance_count_demand_growth_is_concave` で確認した。

- 公演回数を2倍にしても総需要は2倍未満(concave増加)
- 公演回数を増やすほど、1公演あたりの平均需要(カニバリゼーション考慮後)は減少する
- 追加1公演あたりの需要増分は公演回数が増えるほど逓減する

ただし `POOL_EXPONENT=0.85` という値自体は実データに基づく推定ではなく仮置きである点は
1章の通り。将来、同一団体の複数公演間の実際のリピート率・重複購入率データが取得できれば
この指数を再キャリブレーションすべきである。

## 5. Sensitivity Analysis(感度分析)

代表シナリオ(中規模団体・過去2公演・会場キャパ220・価格帯2,500〜5,500円)を基準に、
主要18パラメータを ±10% / ±20% 変化させ、バランス価格・需要・Venue Fit・売上・利益への
影響を計測した(`backend/scripts/sensitivity_analysis.py` で再現可能)。

### High Sensitivity パラメータ(±10%の変化で推奨価格が±5%以上動く)

| パラメータ | ±10%での価格変化 | ±20%での価格変化 | 備考 |
|---|---|---|---|
| **`PRICE_ELASTICITY`** | -10%→+8.11% / +10%→-10.81% | -20%→+21.62% / +20%→-13.51% | **最も感度が高いパラメータ**。価格弾力性の仮置き値が変わると推奨価格が100〜300円超の幅で動く。公開前に業界知見のある人間によるレビューが最も必要な係数 |
| **`SOLD_OUT_BASE_CORRECTION`** | +10%→-5.41% | +20%→-5.41%(同じ価格バケットに収束) | 完売補正が強まるほど基礎集客力が上振れし、より低い価格でも稼働率目標を満たせるため価格が下がる方向に振れる |

### 中程度の感度(価格帯は動かないが、需要・売上・利益・Venue Fitが動く)

- `WEEKEND_HOLIDAY_FACTOR` / `NEW_WORK_FACTOR`: 該当条件が真の場合、係数の変化率がほぼ
  そのまま需要変化率に線形に反映される(±20%変化 → 需要±17〜20%、利益±34%相当)。
  これは乗算モデルの構造上当然の挙動であり不具合ではないが、これらの係数の実証的な
  裏付けがない以上、**利益予測の絶対値を過信しない**運用上の注意が必要。
- `ATTENDANCE_DECAY`: 価格自体は±2.7%程度の変化に留まるが、Venue Fit区分
  (「やや大きい」⇔「適切」)が変化する境界例があった。
- `BALANCE_WEIGHT_OCCUPANCY` / `REVENUE` / `PROFIT`: 重みを変えるとVenue Fit区分が
  変化する場合があるが、価格自体の変化は±2.7%に留まる。

### 低感度パラメータ

`EVENING_FACTOR`、`GUEST_FACTOR`、`SPECIAL_FACTOR`、`LOCATION_RATING_STEP`、
`BRAND_RATING_STEP`、`SNS_FACTOR_SCALE`、`SNS_FACTOR_CAP`、`POOL_EXPONENT`
(このシナリオでは公演回数1回のため影響なし。複数公演シナリオでは支配的になる点に注意)、
`BALANCE_WEIGHT_DISCOUNT_PENALTY` は、代表シナリオにおいて±20%の変化でも
価格変化ゼロ、需要変化1%未満に留まった。

## 6. Recommendation Stability(推奨の安定性)

過去販売枚数を2枚刻みで150〜218まで動かした場合のバランス価格の推移:

```
tickets_sold: 150→180 の範囲では 3,800円 で安定
182→206 の範囲では 3,900円 で安定
208→212 の範囲では 4,000円 で安定
214→216 の範囲では 4,100円 で安定
218        では 4,200円
```

100円刻みの価格探索という設計上、入力の微小変化に対して推奨価格は
**常に隣接する価格ステップ(100円)へ滑らかに移行しており、不連続なジャンプは検出されなかった**。
同様に、SNSフォロワー数の微小変化・会場キャパの微小変化・価格上限のわずかな変化についても
300円(3ステップ)を超えるジャンプは発生しなかった(`tests/calibration/test_recommendation_stability.py`
5件すべてpass)。

## 7. Boundary Test 結果

follower=0、過去動員=0、capacity=1、capacity=5000、price=500/30000、venue_cost=0、
venue_costが売上を大幅に超過、過去公演1件のみの最小入力、全過去公演完売、全過去公演低稼働、
および上記の複合極端値について、**クラッシュは1件も発生せず、すべて有限な数値で返ってきた**。

特筆すべき点:
- **過去動員=0**の場合、基礎集客力は0となり、どんなに小さい会場でもVenue Fitが
  「大きすぎる」と判定される(数学的には正しい挙動だが、実運用では「過去実績が極端に
  少ない/ない団体」への配慮あるメッセージ表示を将来的に検討する余地がある)。
- capacity=5000のような巨大会場では稼働率が20%未満に収まり、SNSやその他補正だけで
  巨大会場を正当化するような推奨は発生しなかった。

## 8. High Sensitivity Parameter まとめ(再掲)

公開前に人間が最優先でレビューすべき係数:

1. **`PRICE_ELASTICITY`(価格弾力性、現在値0.9)** — 推奨価格への影響が最大。
   演劇・コント業界の実際の価格弾力性に詳しい人物のレビューを強く推奨。
2. **`SOLD_OUT_BASE_CORRECTION` / `SOLD_OUT_EARLY_BONUS_PER_DAY` / `SOLD_OUT_CORRECTION_CAP`
   (完売補正、現在1.05 / 0.01日 / 上限1.20)** — 完売公演が多い団体ほど推奨価格・
   Venue Fit判定への影響が大きい。
3. **`POOL_EXPONENT`(公演回数の逓減指数、現在0.85)** — 複数公演シナリオでのみ支配的に
   なるため今回の代表シナリオ(1公演)では感度ゼロと出たが、複数公演を検討する主催者
   ほど実質的な影響が大きい。

## 10. 公開前に人間が判断すべき事項

1. `PRICE_ELASTICITY` と完売補正係数(2. High Sensitivity)について、実際の興行主・
   劇場関係者の感覚と大きく乖離していないか、レビューを受けること。
2. 「本シミュレーションは過去実績と入力条件に基づく参考値です」という免責文言が、
   実際に主催者に正しく認識されるUI配置になっているか(現在は結果画面上部に表示済み)。
3. 過去実績が極端に少ない(0件に近い)新規団体への対応方針
   (現状は「大きすぎる」という警告が強めに出るが、これが新規団体にとって
   不必要に悲観的なメッセージにならないか、文言の再検討余地あり)。
4. 実績登録機能(`actual_results`)によって蓄積されたデータを、いつ・どの基準で
   ML移行の判断材料にするか(`docs/ML_PLAN.md` のBaseline比較方針を運用にどう落とし込むか)。
5. 本レポートの感度分析は「代表シナリオ1件」に基づくものであり、全ての団体規模・
   会場規模の組み合わせを網羅した感度分析ではない。大規模な公開の前には、
   複数の代表シナリオでの感度分析追加実施が望ましい。

理由:

- 実ブラウザE2Eで主要フロー(STEP1〜5、実績登録含む)が正常動作し、発見した不具合
  (実績登録UI欠落)は修正済み。コンソールエラーはPC/スマートフォンともに0件。
- Calibration Test Dataset 100件超、Invariant 9件、Boundary 12件、Scenario 60件、
  Unit 24件の計212件のテストがすべてpassし、極端な入力でもクラッシュや
  「フォロワー数だけで巨大会場を推奨する」「値上げで需要が増えると学習する」
  「完売枚数を真の需要の上限として扱う」といった、最重要原則(`docs/SPEC.md` 5章)に反する
  異常な推奨は1件も検出されなかった。
- 複数公演のカニバリゼーションについても、単純複製ではなく逓減モデルであることを
  数値的に確認済み。
- Recommendation Stabilityの検証で、入力の微小変化による推奨価格の不連続なジャンプは
  検出されなかった。

ただし「限定的ベータ」に留めるべき理由:

- 全27の補正係数が実証データに基づかない仮置きであり、特に`PRICE_ELASTICITY`は
  推奨価格への感度が非常に高い。実際の興行主からのフィードバックを受けながら、
  少人数・限定公開の範囲で係数の妥当性を検証していくべき段階である。
- 感度分析は代表シナリオ1件に基づくものであり、全ケース網羅ではない。
- レートリミット等、`README.md` セキュリティチェックリストの一部項目
  (本番DB切替、CORS本番設定等)は運用担当者が公開時に確認する必要がある(実装済みだが
  未設定の項目あり)。

以上より、**不特定多数への一般公開ではなく、フィードバックを収集しながら係数を
継続的に見直せる体制のもとでの「限定的ベータ公開」は可能**と判断する。
